## 4. 간호사가 배송을 받았다고 알릴 방법이 없음

### 문제 정의
로봇이 병실에 도착해도 간호사가 "받았다"고 EMR에 알릴 수단이 없었다.
배송은 `arrived`(도착)에서 멈추고 `received`(받음)로 끝나지 않는다.
그래서 배송 한 건을 처음부터 끝까지 시험할 수 없었고, 배송 기록도 완성되지 않았다.

### 원인
- 10-20 설계의 수령 방법은 하나뿐이었다. 도착하면 EMR이 일회용 ArUco 마커(`DICT_4X4_250`의 50~249번)를 만들어 간호사 화면에 띄운다. 로봇 카메라가 그 마커를 읽어 `POST /robot/deliveries/{id}/receipt`를 부른다.
- 그런데 **로봇에 마커를 읽는 카메라 노드가 없었다.** Pinky 카메라 마커 노드는 만들어지지 않았고, 팀원 Pinky API도 마커 기능을 꺼 두었다.
- 이 방법은 수령이 로봇에 달려 있다. 간호사가 물건을 이미 손에 들고 있어도 EMR에서는 끝낼 길이 없었다.

### 해결 (10-22, 사용자 결정 "마커는 일단 끄고 간호사도 '받았습니다' 버튼")
- **간호사 화면에 "받았습니다" 버튼을 둔다.** API는 `POST /api/v1/deliveries/{id}/receipt`다.
  - 도착(`arrived`)한 **본인 배송만** 받음(`received`)으로 바꾼다.
  - 도착 전이거나 이미 끝난 배송은 409 `delivery_not_arrived`다.
- **수령 방법을 설정으로 고른다.** `NURSE_RECEIPT_METHOD`가 `button`(기본)이면 버튼, `marker`면 예전 마커 방식이다.
  - 섞이지 않게 막는다. 버튼 방식일 때 로봇이 마커로 받으려 하면 409 `delivery_receipt_by_button`, 마커 방식일 때 버튼을 누르면 409 `delivery_receipt_by_marker`다.
  - 마커 코드는 지우지 않고 남겼다. 일회용 마커도 DB 규칙대로 도착 때 계속 만든다.
- **도착 창.** 도착하면 신청한 간호사 화면에 "배송이 도착했습니다" 창이 뜬다.
  - 창에는 큰 "받았습니다" 버튼과 받을 수 있는 시간(5분, `RECEIPT_WAIT_SECONDS = 300`)이 나온다.
  - 창은 알림(SSE)이 아니라 내 배송 목록을 보고 띄운다. 그래서 새로고침하거나 연결이 끊겨도 다시 나온다(`ReceiptMarkerWatcher`).
- **환자 병상 화면.** 같은 날 병상 단말에도 같은 버튼을 넣었다(`POST /api/v1/bedside/deliveries/{id}/receipt`, 병상 키).

### 결과
- 10-22 띄운 스택에서 신청 → 도착 → 수령 흐름을 확인했다. 백엔드 시험 120개가 통과했다(커밋 `af16120`).
- 10-30 블록도에서 수령 방법을 **버튼으로 확정**했다. 예전 마커 50~249번과 간호사 신분증 마커 0~49번은 수령에 쓰지 않는다.
- 11-02 실물 시험에서 Pinky 3대가 동시에 5회 돌아 **신청 30건 중 29건을 받음까지 끝냈다**(OMX는 가상). 실패 1건은 로봇이 충전기 선에 걸린 것이다.
- 11-03 배송 요청·받음 30초 소개 영상에 이 화면을 썼다.
- 남은 것:
  - 5분 안에 누르지 않을 때 어떻게 할지는 정하지 않았다.
  - 로봇이 수령을 직접 확인하지는 않는다. 대신 간호사의 확인을 믿는다.

관련 파일:
- 백엔드: `emr/backend/app/core/config.py`(`NURSE_RECEIPT_METHOD`), `app/api/v1/deliveries.py`(`confirm_delivery_receipt`), `app/services/delivery.py`(`confirm_receipt`), `app/services/dispatch.py`(마커 방식), `app/api/v1/bedside_access.py`
- 프런트: `emr/frontend/src/features/deliveries/ReceiptMarkerDialog.tsx`(도착 창), `ReceiptMarkerWatcher.tsx`(창 띄우기)

## 10. 시험할 때마다 예약 시각을 미래로 넣고 기다려야 함

### 문제 정의
배송 신청은 "보낼 시간(`scheduled_at`)"을 받는다. 지금 바로 보내는 신청을 넣을 수 없었다.
- 시각을 지금으로 넣으면 요청이 서버에 닿는 사이 과거가 되어 400 `scheduled_at_not_future`로 거절됐다.
- 그래서 시험 때마다 몇 분 뒤 시각을 넣고 그 시각이 될 때까지 기다려야 했다.
- 10-22 팀원 로봇이 처음 연결되는 날, 신청 → 맡기 → 도착 → 수령을 빠르게 반복할 수 없었다.

### 원인
- 예약 시각 검사가 "지금보다 미래"만 허용했다(`DeliveryService._validate_scheduled_at`).
- 간호사가 고른 "지금"은 요청이 서버에 닿을 때 이미 몇 초 과거다. 브라우저와 서버의 시계가 다르면 더 벌어진다.
- 로봇은 보낼 시간이 된 배송만 가져간다. 그래서 미래로 넣으면 그만큼 기다려야 했다.

### 해결 (10-22)
- **5분 전까지의 과거 시각을 받는다.**
  ```python
  SCHEDULED_AT_GRACE = timedelta(minutes=5)   # "지금"(브라우저·서버 시계 차이 포함)으로 예약하면 바로 로봇이 가져갈 수 있다

  if scheduled_at < datetime.now(UTC) - SCHEDULED_AT_GRACE:
      raise BadRequest("scheduled_at must not be in the past", code="scheduled_at_not_future")
  ```
- 5분보다 더 과거면 지금처럼 400이다. 잘못 넣은 옛 날짜는 계속 막는다.
- DB와 API 형식은 바뀌지 않았다.

### 결과
- 10-22에 "지금" 신청이 바로 맡을 수 있는 배송이 되었다. 같은 날 헤더 없이 4번 호출해 신청부터 받음까지 확인했다(시험 배송 #27).
- 10-30 이 여유를 바탕으로 신청 화면에 **'즉시' 버튼**을 만들었다(`a154892`, 프런트만).
  - '즉시'는 누른 순간의 시각으로 신청한다.
  - 백엔드는 그 신청을 받아 다음 회차(5초 안)에 FMS로 주문을 보낸다.
- 10-30 연속 운전 시험은 간호사 화면에서 '즉시' 신청을 90초마다 넣었다. 11-02 실물 시험도 '즉시'와 예약 신청을 섞어 썼다.
- 주의:
  - 5분 안의 과거 시각은 받자마자 보낼 대상이 된다. 그래서 정한 시간에 보내려면 '시간 지정'을 써야 한다.
  - 11-02 NO 361·362는 예약 신청이라 정한 시각 전까지 '예약'에 머물렀다. 이것은 정상이다.

관련 파일: `emr/backend/app/services/delivery.py`(`SCHEDULED_AT_GRACE`, `_validate_scheduled_at`), `emr/frontend/src/features/deliveries/DeliveryForm.tsx`('즉시'·'시간 지정')
