# Pinky 여러 대 운영 구조 (제안, 2026-10-20)

- **독자**: 팀원 전체 — 웹(EMR), 로봇(Pinky·관제), OMX
- **한 줄 요약**: Pinky 여러 대가 같은 병원 맵을 함께 쓰며 EMR 배송을 나눠 맡는다. 이를 위해 **로봇 웹서버 대신 관제 PC 프로그램 하나**가 모든 로봇을 맡고, 로봇은 **ROS 도메인 번호로 구분**하며, **맵은 같은 파일을 모든 로봇에 복사**한다.
- **상태**: 제안. 코드는 아직 바꾸지 않았다. 7장 열린 질문에 팀 의견을 받는다.
- **근거**: 2026-10-20 실물 Pinky 1대를 관제 PC에서 읽어 확인한 값. 상세 실측은 `pinky_analysis_2026-10-20.md`.

## 1. 배경

### 1.1 우리가 만들려는 것
간호사가 EMR 웹에서 비품 배송을 예약하면 Pinky가 병실로 가져다준다. EMR 로드맵 6단계는 **Pinky 3대**를 같은 병동에서 함께 쓰는 것이다.

### 1.2 2026-10-20까지 확인된 것
| 확인한 것 | 결과 |
|---|---|
| EMR에 올린 병원 맵 = 로봇 Nav2 맵 | 크기 271×359 px, 0.02 m/px, 원점 (−1.801, −6.847) 일치 |
| EMR 장소 좌표로 실제 주행 | `test_waypoint.py 비품실` → 29초, Nav2 결과 **성공** |
| 관제 PC에서 로봇 상태 읽기 (`robot_monitor`) | 위치·속도·배터리(45 %, 7.16 V)·주행 결과 모두 수신 |

즉 **한 대는 EMR 좌표로 움직인다.** 이제 여러 대로 늘리기 전에 구조를 정해야 한다.

### 1.3 지금 구조로는 여러 대가 안 되는 이유
1. **네트워크**: Pinky가 각자 와이파이 AP(`192.168.4.1`)를 띄운다. PC 무선랜은 한 번에 한 AP에만 붙으므로 로봇 두 대를 동시에 볼 수 없다. 실제로 PC가 Pinky AP에 붙자 병원 LAN 주소가 사라져 다른 PC에서 EMR 웹에 못 들어왔다.
2. **로봇 웹서버의 한계**: 지금 시험 도구는 Pinky의 Flask 웹서버(:8080)를 거친다. 이 서버는 로봇마다 따로 있고, 주행 결과·배터리를 주지 않으며, 상태 응답 한 번이 466 KB다(2장).
3. **ROS 이름 충돌**: Pinky는 모두 같은 토픽 이름(`/scan`, `/cmd_vel`, `/map` …)을 쓴다. 같은 ROS 네트워크(도메인)에 두 대를 올리면 서로 섞인다.
4. **Pinky 코드의 namespace 지원 불완전**: 이름을 나누는 표준 방법(namespace)을 Pinky upstream이 완전히 지원하지 않는다(4장 결정 2).

## 2. 목표 시나리오 (여러 대가 함께 쓰는 흐름)

```
간호사 (EMR 웹)  ──예약──▶  EMR (api + db)
                                 ▲  │  배송 가져가기(claim) · 진행 보고 (로봇별 키)
                                 │  ▼
                      관제 PC 프로그램 (하나)
                      ├─ 상태 수집: 로봇별 위치·배터리·주행 결과
                      └─ 배송 실행: 빈 로봇에 배송 → Nav2 목표 → 결과 보고
                         │ ROS 도메인 11      │ 도메인 12        │ 도메인 13
                         ▼                    ▼                  ▼
                      Pinky 1              Pinky 2            Pinky 3
                      (같은 map_rev2 파일로 각자 위치 추정·주행)
```

1. 간호사가 배송을 예약한다(지금 가능).
2. 예약 시각이 되면 관제 프로그램이 **비어 있는 로봇**을 골라 EMR에서 배송 한 건을 가져온다(claim).
3. 관제 프로그램이 그 로봇의 도메인으로 목적지(EMR 장소 좌표)를 Nav2에 보낸다.
4. 출발·도착·실패를 EMR에 보고하고, 간호사 화면에 단계와 알림이 뜬다.
5. 수령 확인 뒤 로봇은 복귀 장소로 돌아간다.
6. 로봇 위치·배터리는 관제 프로그램이 모아 EMR 맵 화면에 한꺼번에 보여 준다.

## 4. 결정별 이유

### 결정 1. 로봇 웹서버 대신 관제 PC 프로그램

**선택지**: (A) Pinky 웹서버(Flask :8080)를 계속 쓴다 / (B) 관제 PC에서 ROS로 직접 상태를 받고 명령을 보낸다.

같은 로봇에 둘 다 붙여 잰 값:

| 항목 | Pinky 웹서버 | 관제 PC (`robot_monitor`) |
|---|---|---|
| 상태 응답 크기 | 1회 **466 KB** (맵 295 KB + 코스트맵 369 KB, 위치는 78 B) | 로봇당 수백 B |
| 배터리 | 없음 | 있음 |
| 끊김 판단 | 없음 | 3초 무소식이면 offline |
| 실시간 전달 | 계속 물어야 함 | SSE 1초, ROS 토픽 |
| 주행 결과 | 없음 (주행 중인지만) | 성공·취소·실패 |
| 여러 대 | 로봇마다 주소 따로 | 한 곳에 모음 + EMR 로봇 id 연결 |
| 로봇 부담 | 라즈베리파이가 Flask·맵 직렬화 | 로봇은 원래 토픽만 냄 |
| 코드 소유 | upstream (수정 금지) | 우리 코드 |

**결정: B.** 이유:
1. 비품실 시험에서 웹서버로는 성공 여부를 알 수 없었다(위치 0.28 m로 짐작). 관제 PC는 Nav2 결과 "성공"을 바로 받았다. 배송 단계 보고에는 정확한 결과가 필요하다.
2. EMR 화면에 로봇 위치·배터리를 실시간으로 보이려면 웹서버로는 1초에 466 KB씩 받아야 하고 배터리도 없다.
3. 로봇이 늘어도 관제 프로그램 하나에 설정만 추가하면 된다.

명령은 이렇게 바뀐다:

| 역할 | 웹서버 방식 (지금 시험 도구) | 관제 PC 방식 |
|---|---|---|
| 로봇 실행 | `web_nav2.launch.xml map:=…` | `bringup_launch.xml map:=…` (Nav2만) |
| 이동 | `POST /api/goal` | `navigate_to_pose` 액션 |
| 초기 위치 | `POST /api/initialpose` | RViz2 2D Pose Estimate 또는 `/initialpose` |
| 정지 | `POST /api/nav/stop` | 액션 취소 |
| 사람이 보는 화면 | 로봇 웹페이지 | 관제 PC의 RViz2, 나중에 EMR 맵 화면 |

웹서버는 사람이 로봇 하나를 손으로 볼 때만 선택적으로 띄운다.

### 결정 2. 로봇마다 ROS 도메인 번호

**선택지**:

| | A. 로봇마다 도메인 | B. 같은 도메인 + namespace | C. Zenoh 통신 |
|---|---|---|---|
| 방법 | Pinky 1=11, 2=12, 3=13. 각 로봇은 한 대일 때와 똑같이 실행 | `/pinky_1/scan`, `/pinky_2/scan` … | 통신 계층을 rmw_zenoh로 교체 |
| Pinky 쪽 작업 | 로봇 `~/.bashrc`에 `export ROS_DOMAIN_ID=11` 한 줄 | `bringup_robot.launch.xml`에 namespace 인자 없음, Nav2 설정이 `/scan`을 절대 경로로 씀(`nav2_params.yaml` 202·234줄, `mapper_params.yaml` 16줄), 프레임 접두사 처리 → 우리 launch·설정으로 덮어써야 함 | 로봇·PC 모두 교체, 이 PC에 미설치 |
| 와이파이 부담 | 로봇끼리 데이터를 주고받지 않음 | 모두 한 도메인에서 서로를 발견·교환 | 가장 적음 |
| 관제 PC | 한 프로그램이 로봇별 도메인에 동시에 붙음 | 한 도메인 | 라우터 추가 |
| 한 RViz 화면에 모든 로봇 | 안 됨 (로봇마다 RViz) | 됨 | — |

**결정: A.** 이유:
1. **upstream을 고치지 않는다.** 로봇은 한 대일 때 실행법 그대로다. B는 Pinky 코드가 namespace를 완전히 지원하지 않아 우리 쪽 덮어쓰기가 많다.
2. **와이파이 부담이 준다.** Pinky README는 여러 대를 한 공유기에 붙이면 ROS 통신량으로 끊길 수 있다고 경고한다. 도메인이 다르면 로봇끼리 데이터를 주고받지 않는다.
3. **관제 프로그램 하나로 된다.** 한 파이썬 프로세스가 도메인 11과 12에 동시에 붙는 것을 시험해 확인했다(`rclpy.init(context=…, domain_id=…)`).
4. 잃는 것(RViz 한 화면에 모든 로봇)은 EMR 맵 화면(로드맵 3단계)이 대신한다.

### 결정 3. 맵은 같은 파일을 모든 로봇에 복사

**질문**: 여러 대가 같은 맵을 쓰려면 namespace가 필요한가? → **아니다.**

"맵 공유"는 모든 로봇이 **같은 좌표계**로 위치를 잡고 주행하는 것이다. 같은 맵 파일을 각 로봇이 자기 `map_server`로 읽으면 좌표계가 같아진다. EMR 장소 (0.44, −1.55)는 1호기든 2호기든 같은 지점이다.

| 하고 싶은 것 | namespace 필요? | 우리 방식 |
|---|---|---|
| 같은 맵으로 각자 주행 | 아니요 | 같은 파일을 로봇마다 복사 |
| 맵 하나를 PC에서 모든 로봇에 제공 | 같은 도메인이면 예 | 필요 없음 (복사가 더 단순) |
| 한 RViz에 모든 로봇 | 예 | EMR 맵 화면으로 대신 |
| 로봇끼리 서로의 위치를 ROS로 직접 받기 | 예 | 하지 않음. 관제가 위치를 모으고, 로봇끼리는 라이다 장애물로 피함 |
| 여러 대가 함께 지도 만들기(다중 SLAM) | 예 + 맵 병합 | 해당 없음 (고정 맵) |

namespace를 쓰면 오히려 번거롭다. namespace로 띄운 Pinky의 AMCL·Nav2는 `/pinky_1/map`처럼 자기 이름 아래의 맵을 찾으므로, 결국 로봇마다 `map_server`를 두거나 공용 `/map`으로 이어 주는 설정이 따로 필요하다.

**맵 배포 절차**:
1. 관리자가 EMR에 맵(yaml + pgm/png)을 올린다 — 기준은 EMR.
2. 관제 PC에서 꺼낸다: `python3 robot/src/fms/test_waypoint/emr_map_export.py 병원 robot/maps`
3. 모든 로봇의 같은 경로로 복사한다: `scp robot/maps/map_rev2.* pinky@<로봇 IP>:~/maps/`
4. 로봇마다 `map:=/home/pinky/maps/map_rev2.yaml`로 Nav2를 띄운다.
5. 관제 프로그램이 출발 전에 로봇마다 맵이 EMR과 같은지(크기·해상도·원점) 확인하고, 다르면 그 로봇에는 배송을 주지 않는다(`test_waypoint`에 이미 있는 검사).

맵을 바꾸면 2–4를 모든 로봇에 다시 한다. EMR 장소 좌표는 자동 변환되지 않으므로 원점이 바뀌면 장소를 다시 찍는다(emr/CLAUDE.md).

### 결정 4. 네트워크는 공유기 하나

- 모든 Pinky를 **병원 공유기 하나**에 붙인다(Pinky Studio 앱 WiFi 설정).
- 공유기에서 로봇마다 **고정 IP**를 준다.
- 관제 PC는 공유기에 **유선**으로 붙인다. 그러면 간호사 PC도 같은 공유기로 EMR에 들어온다.

## 5. 운영 규칙 (제안)

### 5.1 번호·이름

| 로봇 | ROS 도메인 | 고정 IP | 관제 이름 | EMR 로봇 |
|---|---|---|---|---|
| Pinky 1 | 11 | 공유기에서 지정 | `pinky_1` | id 1 배송로봇 1호 |
| Pinky 2 | 12 | 〃 | `pinky_2` | id 3 배송로봇 2호 |
| Pinky 3 | 13 | 〃 | `pinky_3` | id 4 배송로봇 3호 |

- EMR id는 현재 DB 값(id 2는 적재 매니퓰레이터).
- 피할 번호: **0**(기본값, 아무 기기나 섞임), **56**(OMX 팔 작업), **77**(Claude 시험).
- 지금 시험 중인 Pinky 1대는 도메인 **0**이다 → 11로 옮긴다.

### 5.2 동시에 움직일 때
- Nav2는 다른 Pinky를 **라이다에 보이는 장애물**로만 피한다. 로봇끼리 길을 양보하거나 순서를 정하는 기능은 없다(어느 방식이든 같음).
- 지금 공간은 약 2.2 × 2.0 m로 좁다. 처음에는 관제가 **한 번에 한 대만** 출발시키고, 익숙해지면 구역을 나눈다.
- 비품실처럼 못 가는 곳을 막는 Nav2 금지 구역 필터는 아직 없다(`filters: []`). 당분간 장소 목록에서 뺀다.
