# 시나리오 ① 여러 병동 한 번에 신청 → 묶음 배송 (2026-10-30)

간호사가 한 번의 신청으로 여러 병동에 물품을 보내고, FMS가 로봇 한 대에 묶어 차례로 도는 것을 보인다.
관련: 계약 `docs/api_contract_delivery_2026-10-20.md` 10장, FMS `fms/API.md`.

## 0. 주문 단위 — 신청 · FMS 주문 · 묶음

| 단위 | 누가 만드나 | 크기 | 코드 |
|---|---|---|---|
| **신청(배송) 1건** | 간호사 → EMR | **병동 1곳 + 물품 여러 종류·여러 개** | `POST /deliveries` |
| 여러 병동 신청 | 간호사 → EMR | 화면에서는 한 번, EMR 안에서는 **병동마다 신청 1건씩** 생긴다. 모두 되거나 모두 안 된다(재고는 합계로 확인) | `POST /deliveries/multi` (10-30) |
| **FMS 주문 1건** | EMR → FMS | **물품 1개 + 방 1곳** (A 약품 2개면 주문 2건) | `services/fms_order.py`, `request_id = emr-d{배송}-s{비품}-{n}` |
| **묶음 1개** | FMS | **로봇 1대가 한 번에 싣는 주문 최대 3건** = 방 최대 3곳. 로봇의 지금 오염도 + 병실 오염도가 100을 넘으면 넣지 않는다. 수술실은 오염도 0일 때만 | `fms_core.py` `bundle_from`, `cap = 3` |

예: 101호에 A 2개 + 103호에 B 1개 + 104호에 C 1개를 한 번에 신청
→ EMR 신청 3건 → FMS 주문 4건 → 묶음 2개(3건 + 1건), 로봇 2대.

화면 단계는 **신청 1건 단위**로 바뀐다.
- **준비**: 그 신청이 든 묶음에 로봇이 불려 갈 때(`robot_called`).
- **출발**: 약제실 정밀 주차가 끝났을 때.
- **도착**: 그 신청의 물품이 **모두** 배송됐을 때(`order_delivered`가 물품 수만큼 온 뒤).

한 신청의 물품이 두 로봇으로 나뉘면, 늦게 오는 로봇이 도착해야 도착이 된다.

## 1. 준비

| 항목 | 값 |
|---|---|
| FMS | **시뮬레이터(가상 Pinky) + 가상 OMX**로 리허설. 실물 Pinky로 하는 것은 따로 정한다 |
| FMS 띄우기 | `cd ~/dev_ws/fms && FMS_ARGS="--robots 3" CONTROL_URL=http://<EMR IP>:8000 docker compose up -d --build`(10-30 팀원 코드 반영). `FMS_ARGS`를 비우면 실물 모드(`--real-table`)가 된다 |
| EMR `.env` | `FMS_OMX_ENABLED=0`(가상 OMX), `FMS_PHARMACY_SIGNAL=fms` |
| 계정 | 간호사 N002 / nurse1234 |
| 화면 | EMR 신청 화면, 병원 지도(로봇 카드), 배송 기록 / FMS 화면 `http://<이 PC>:8770` |
| 시작 상태 | 로봇 3대 모두 대기(오염도 0, 피로도 100). 진행 중인 신청 없음 |

**묶음으로 모으기**
- EMR은 5초마다 보낼 시간이 된 신청을 FMS로 보낸다.
- FMS는 0.05초마다 배차하므로, 주문이 다 오기 전에 첫 주문만 실은 로봇이 먼저 떠날 수 있다.
- 한 묶음을 확실히 보이려면 보낼 시간 전에 FMS를 멈추고, 주문이 다 들어오면 다시 켠다.

```bash
curl -s -X POST http://127.0.0.1:8770/api/control -H 'Content-Type: application/json' -d '{"paused": true}'
# … 주문이 모두 waiting으로 들어온 것을 FMS 화면에서 확인한 뒤
curl -s -X POST http://127.0.0.1:8770/api/control -H 'Content-Type: application/json' -d '{"paused": false}'
```

## 2. 장면 A — 3개 병동, 각 1개 → 로봇 1대

| # | 누가 | 하는 일 | 기대 결과 / 확인 |
|---|---|---|---|
| A1 | 간호사 | 신청 화면에서 **+ 병동 추가**로 101호(4인실) A 약품 1, 103호 B 약품 1, 104호 C 약품 1을 넣는다. 보낼 시간은 1~2분 뒤 | 신청 3건이 **예약**으로 생기고, 재고가 각 1씩 준다 |
| A2 | 진행자 | 보낼 시간 직전에 FMS를 멈춘다 | — |
| A3 | EMR → FMS | 보낼 시간에 주문 3건을 보낸다 | FMS 화면에 주문 3건이 `waiting`. EMR 신청은 아직 **예약** |
| A4 | 진행자 | FMS를 다시 켠다 | FMS가 묶음 1개를 만든다(`batch_assigned`, 101·103·104호). 오염도 합 50+10+10 = 70 ≤ 100 |
| A5 | FMS → EMR | 로봇을 약제실로 부른다(`robot_called`) | 신청 3건이 모두 **준비**. 병상 화면: "약제실에서 물품을 준비하고 있습니다." 지도 카드에 그 로봇이 **배차됨 → 이동** |
| A6 | 가상 OMX | 15초 뒤 준비 완료(`ready`) | — |
| A7 | FMS | 약제실 정밀 주차 20초 | 카드 **정밀 주차**. 끝나면 신청 3건이 **출발**, 간호사 알림 |
| A8 | 가상 OMX | 적재 10초(`loaded`) | 카드 **적재 대기** → **이동** |
| A9 | Pinky | 가까운 병실부터 돈다. 병실마다 제자리 한 바퀴(8초) | 병실마다 그 신청만 **도착**. 지도 카드 피로도 −10씩(100 → 70), 오염도 +50·+10·+10(→ 70) |
| A10 | 간호사 | 병실마다 **받았습니다** | 그 신청이 **수령**. 배송 기록에 신청 → 준비 → 출발 → 도착 → 수령 시각 |
| A11 | FMS | 묶음 끝(`batch_completed`). 그다음 일(오염 제거·다음 배송·주차)은 FMS가 정한다 | 카드 상태가 FMS 값대로 바뀐다(EMR은 표시만) |

## 3. 장면 B — 넘치면 로봇 2대로 나뉜다 (선택)

| # | 하는 일 | 기대 결과 |
|---|---|---|
| B1 | 101호 A 약품 **2개**, 102호 B 1, 103호 C 1을 한 번에 신청(신청 3건, FMS 주문 4건) | — |
| B2 | 장면 A처럼 멈췄다가 주문 4건이 들어오면 다시 켠다 | 묶음 2개. 101호 2개는 한 방이라 한 번만 들르고, 101호 + 102호는 오염도 100으로 한계다. 먼저 들어온 주문부터 가까운 병실을 채우므로 보통 **로봇 1 = 101호 2개 + 103호**, **로봇 2 = 102호**. 실제 배정은 FMS 화면 묶음 칸으로 확인한다 |
| B3 | 진행 | 두 로봇이 각자 준비 → 출발 → 도착. 신청마다 따로 도착·수령 |

## 4. 끝나고

- FMS를 시작 전 상태로 돌린다(멈춤 또는 `docker compose stop`).
- 시험 신청은 배송 기록에 남는다. 지울지는 그때 정한다.

## 확인할 점

- 피로도(10-30 `battery`에서 이름 바뀜)·오염도는 **FMS가 계산한 모델 값**이다. 실제 배터리나 센서 값이 아니다.
- 다른 신청이 waiting에 있으면 같은 묶음에 섞일 수 있다. 시연 때는 그 전 신청을 비운다.
- 실물 Pinky로 하면 로봇이 실제로 움직인다. FMS는 켜자마자 로봇을 주차 자리로 보낸다.
