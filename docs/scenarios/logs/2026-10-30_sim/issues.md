## 2. FMS가 멈춰도 EMR이 모름 (FMS ↔ EMR)

- 교착 동안에도 FMS는 `POST /api/v1/orders`를 정상으로 받았다(202). robot-status도 1초마다 왔다(`online` true, state `waiting`).
- `robot_error` 같은 이벤트는 오지 않았다. EMR은 "로봇이 오래 멈춤"을 알 수 없다.
- 제안:
  - FMS가 한 로봇이 N초 넘게 `waiting`이면 이벤트를 보낸다(예: `robot_error` `code=stuck`).
  - 또는 EMR이 robot-status를 보고 판단한다. 같은 자리 + `waiting`이 N분 넘으면 관리자에게 알린다. 다만 이것은 EMR이 FMS 상태를 해석하는 일이라, 먼저 역할을 정한다(EMR은 표시만).

## 3. 멈춘 신청이 화면에 끝없이 남음 (EMR)

- 예약·준비 상태에 시간 제한이 없다. 간호사 화면에 "곧 운반 로봇이 출발합니다", "약제실에서 물품을 준비하고 있습니다"가 계속 보인다.
- 한 개라도 FMS로 보낸 신청은 간호사가 변경·취소할 수 없다(409 `delivery_sent_to_fms`). FMS 취소 연동(`DELETE /orders`)이 아직 없기 때문이다.
- 제안: 정해진 시간(예: 신청 시각 + N분)을 넘긴 신청을 화면에 '지연'으로 표시하고 관리자에게 알린다. FMS 취소 연동이 생기면 간호사 취소를 연다.

## 4. FMS를 다시 켜면 신청이 고아가 됨 (FMS ↔ EMR)

- FMS는 주문을 메모리에만 둔다. 다시 켜면 `o-1`·`b-1`부터 다시 시작한다.
- EMR의 남은 신청은 FMS에 없는 주문을 기다리며 그대로 남는다.
- 지금 남아 있는 것:
  - N003: NO 94~128 (35건, 이번 교착)
  - N002: NO 69~73 도착에서 멈춤, NO 74 출발에서 멈춤 (10-29 실물 시험 뒤 FMS 재시작)
- 이미 `emr/CLAUDE.md`에 남은 일("FMS 다시 시작 대응")로 적혀 있다. 정리 방법(실패 처리 + 재고 복구, 또는 다시 보내기)을 정해야 한다.

## 5. FMS 칸 이름 변경 — 고침

- 팀원이 10-30 robot-status의 `battery`를 `fatigue`(피로도)로 바꿨다. pull 뒤 EMR 지도 카드의 배터리가 "—"로 나왔다.
- EMR이 `fatigue`를 읽게 고쳤다(`332f2ba`, API `fatigue_percent`, 카드 '피로도').
- 앞으로 FMS ↔ EMR 칸을 바꿀 때는 계약 문서(`docs/api_contract_delivery_2026-10-20.md` 10장)를 먼저 고치고 양쪽에 알린다.

## 부록: 시험 도구에서 겪은 것 (시스템 문제 아님)

- 한 브라우저에 탭 두 개로 녹화하면 뒤 탭(지도)은 숨은 화면이라 1초 갱신을 멈춘다. 그래서 장면 A 1차 영상에서 지도가 멈춰 보였다. 화면마다 브라우저를 따로 띄워 고쳤다.
- 녹화 폴더를 같이 써서 장면 A 1차의 자막 기록이 2차에 덮였다. 1차 진행 흐름은 배송 기록(DB) 시각으로 대신했다. 지금은 시험마다 폴더를 따로 쓴다.
