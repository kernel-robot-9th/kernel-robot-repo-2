# FMS 시뮬레이터 + 관제 PC API v1

실제 로봇 없이 FMS(배차·배송 묶음·오염도·피로도·구간 예약·교행 금지)를 가상 핑키 3대로 돌려 보는 서버다.
**관제 PC 팀은 이 서버에 API v1 로 붙어서 개발·시험하면 된다.** 실제 FMS 도 같은 API 를 연다.

- API 문서: [`API.md`](API.md) (Swagger: 서버를 띄우고 `http://<FMS>:8770/docs`)
- 지도: 같은 저장소 `driving/graph/graph.yaml`(주행 그래프), `driving/tools/real_walls.yaml`(벽)을 그대로 읽는다 → **`driving/` 폴더도 있어야 돈다**.
  그래프를 바꾸려면 `driving/graph/graph_spec.yaml` 을 고치고 `python3 driving/graph/build_graph.py`.

## 1. 실행

필요한 것: Python 3.8 이상, PyYAML (`pip install pyyaml`). 그 밖엔 표준 라이브러리만 쓴다.

```bash
git clone git@github.com:kernel-robot-9th/kernel-robot-repo-2.git
cd kernel-robot-repo-2
git checkout fms
python3 fms/sim_server.py                     # 내 PC 에서만: http://localhost:8770
python3 fms/sim_server.py --host 0.0.0.0      # 다른 PC(관제 PC)에서도 접속
```

| 옵션 | 뜻 |
| --- | --- |
| `--host 0.0.0.0` | 같은 공유기의 다른 PC 에서 접속 허용 (기본은 이 PC 만) |
| `--port 8770` | 포트 |
| `--control-url http://<관제 PC IP>:8000` | 로봇 상태(1초마다)와 이벤트를 이 주소로 POST (`/api/v1/fms/robot-status`, `/api/v1/fms/events`) |
| `--no-auto-omx` | 가상 OMX 끔: OMX 준비 완료(`ready`)·적재 완료(`loaded`)를 관제 PC 가 보내야 핑키가 움직인다 |

## 2. 관제 PC 와 붙여 보기

```bash
# FMS 쪽 (시뮬레이터를 돌리는 PC)
python3 fms/sim_server.py --host 0.0.0.0 --control-url http://<관제 PC IP>:8000 --no-auto-omx
```

관제 PC 쪽 순서 (자세한 형식은 [`API.md`](API.md)):

1. 배송 요청: `POST http://<FMS IP>:8770/api/v1/orders` `{"request_id": "pc-0001", "room": "101호", "item": "진통제"}`
2. FMS 가 `batch_assigned` 이벤트로 묶음(주문 목록 + 맡은 핑키)을 보낸다 → OMX 가 물품 준비
3. 준비가 끝나면 `POST /api/v1/batches/{batch_id}/ready` → 핑키가 약제실로 온다
4. `robot_at_pharmacy` 이벤트가 오면 OMX 가 싣고 `POST /api/v1/batches/{batch_id}/loaded` → 핑키가 병실로 간다
5. 병실마다 `order_delivered`, 마지막에 `batch_completed`. 로봇 위치·상태는 1초마다 `robot-status` 로 온다

관제 PC 서버 없이 확인만 하려면: `curl http://<FMS IP>:8770/api/v1/events?after=0` (최근 이벤트), `curl …/api/v1/state` (지금 상태).

방 번호: 101호~108호, 수술실 (약제실은 상태 표시용, 주문 목적지 아님). 로봇 번호 1~3 ↔ 핑키 이름은 [`robots.yaml`](robots.yaml).

## 2-1. 실제 핑키로 (관제 PC 에서 도커, 2026-10-29)

`robots.yaml` 에 `url` 이 있는 로봇은 실제 핑키로 움직인다 (`--real-table`). 핑키 API(`driving/api`, 포트 8080)의
`POST /drive` · `POST /action` 을 보내고 `GET /status` 를 0.3초마다 읽는다 (`robot_link.py`).

```bash
cd fms
CONTROL_URL=http://<관제 서버>:<포트> docker compose up -d --build     # 화면·API: http://<관제 PC>:8770
docker compose logs -f fms
```

- 로봇 주소: `robots.yaml` 의 `url` (DHCP 라 바뀔 수 있음 — `curl http://<IP>:8080/status` 의 `robot.serial` 로 확인).
  컨테이너에 붙여 쓰므로 고친 뒤 `docker compose restart fms`. 시리얼이 표와 다르면 그 로봇은 오류로 둔다.
- 띄우기 전: 핑키마다 노드 위에 놓고 위치 맞추기 (`POST <로봇>:8080/set_pose {"find": true}`). FMS 는 로봇이 보고한 노드에서 시작한다.
- **띄우면 바로 움직인다**: 노는 로봇은 주차 자리로, 주문이 오면 배송. 실제 로봇이 있으면 시간은 1배속만.
- 이동 = 계획(CBS)에서 다음 대기 지점까지 묶어 `/drive`. 정밀 주차 = `PHARMACY → PHARMACY_DOCK` 엣지, 병실 = `/action spin`.
- 늦음 (엣지가 예상 × 1.5 + 2초 넘음) → 다시 계획. 실패 → 그 자리를 차지한 채 멈춤 + 관제 PC 에 `robot_error`.
  사람이 확인한 뒤 `POST /api/control {"clear_fault": "R1"}` → 엣지 중간이면 `"@here"` 로 마저 가고 이어서.
- 가상 로봇만: `FMS_ARGS="--no-auto-omx" docker compose up -d` (가상 OMX 까지 켜려면 `FMS_ARGS=" "`).
- 도커 없이: `python3 sim_server.py --host 0.0.0.0 --real-table --no-auto-omx --control-url <URL>`
  (한 대만: `--real pinky_6364=http://192.168.129.68:8080 --robots 3` → 나머지는 가상).

## 3. 화면 (http://<FMS IP>:8770)

- **주문 넣기**: 방 버튼 하나 = 주문 1건. **자동 주문**(분당 N건), **배속**, **로봇 수**, **경로**(A*+CBS / 최단 경로+예약), **다시 시작**.
- **가상 OMX** 체크: 켜면 `ready`(배차 15초 뒤)·`loaded`(주차 10초 뒤)를 시뮬레이터가 스스로 보낸다.
  끄면 **묶음** 칸에 "준비 완료"·"적재 완료" 버튼이 생겨 사람이 관제 PC 대신 누를 수 있다. 진짜 관제 PC 를 붙일 땐 끈다.
- 지도: 굵은 색 = 로봇이 예약한 구간, 점선 = 남은 경로, 바깥 고리 = 물품 실음, 네모 = 주차 자리.
- 로봇 카드: 상태(이동·OMX 준비 기다림·정밀 주차·적재·배송 회전·충전 …), 피로도, 오염도, 적재, 맡은 주문, 계획(목적지별 도착~떠날 시각).

## 4. 화면 없이 시험

```bash
python3 fms/run_headless.py --minutes 120 --rate 2 --seed 1     # --robots 2, --planner reserve(예전 방식), --legs 1
```

위반(오염도·피로도·수술실), 몸체 충돌, 실은 로봇끼리 나란히, 가장 오래 기다린 시간, 평균 배송 시간을 센다.

## 6. 주요 규칙 (2026-10-27)

- 주문 1건 = 물품 1개. 핑키 한 대가 한 번에 최대 3건(묶음). 맡은 주문 수만큼만 싣고, 배차 때 정한 묶음은 바꾸지 않는다.
- 핑키는 배차되면 제자리에서 OMX 준비(`ready`)를 기다린 뒤 약제실로 간다.
- 병실에 도착하면 제자리 한 바퀴 = 배송 완료. 다음 일이 있으면 1~5초 쉬고 출발.
- 오염도: 1인실 +10, 4인실 +50, 100 까지. POCKET 5초 = 0. 수술실은 오염도 0 에서만.
  배송은 오염도가 0 이 아니어도 준다 — 단 POCKET 을 들르지 않고 끝낼 수 있는 묶음만 (10-29 사용자).
- 피로도(가상 값, 실제 핑키 배터리 아님): 병실 하나당 −10, 20 이하면 약제실 금지·충전. 충전 = CHARGER 도착 10초 뒤 100.
- 협로 1대, 교행통로에서 실은 로봇끼리 교행 금지(같은 방향 따라가기 허용), 방 사이로 다니지 않음.

# 개발 메모

## 가상 시간 (fms_core.Params)

엣지 시간 = **실측** (`graph/edge_times.yaml`, 방향별 중앙값, 10-27~29 pinky_6364·ee3a), 제자리 회전 = 실측 식 (≈ 1.9 s + 1.8 s/90°), 실측이 없는 엣지만 4.5 cm/s. OMX 준비 15 s·적재 10 s(가상 OMX 일 때), 정밀 주차 20 s, 병실 회전 8 s + 쉬기 1~5 s, POCKET 5 s, 충전 10 s, 적재 최대 3개.

## 경로 계획: A* + CBS (`planner.py`, 기본값)

- 시간 1초 칸, 엣지 시간 = ceil(실측 이동 시간). A* 상태에 **방향**이 들어 있어서, 엣지를 타기 전에 그 엣지 방향으로 제자리 회전(실측 회전 시간, 그동안 노드 점유)을 계획에 넣는다. 로봇이 차지하는 것 = 노드에 머묾(회전 포함) [t0, t1] / 엣지 지남 [t0, t1].
- 시뮬레이터도 엣지마다 실측 속도로 움직인다 (계획과 실행이 같은 시간표). 차례를 기다리느라 서 있는(출발 전) 로봇이 다른 로봇 길을 막으면 비켜 선다 (10-29: 실측 시간에서 T2_190 교착 발견).
- 충돌 = 시간이 겹치고 자리가 부딪힘: 같은 노드·14.5 cm 안 노드·엣지가 가까이 지나는 노드·같은 엣지/끝점,
  같은 1대 zone, 실은 로봇끼리 같은 복도 다른 차선에서 x 범위 14.5 cm 안.
- 아래 단계 = 시공간 A* (우측통행 반대 차선 벌점, 엣지마다 +0.1 = 괜히 돌아다니지 말고 제자리 대기, 휴리스틱 = 남은 목적지까지 최단 시간 + 머무는 시간).
  위 단계 = CBS (충돌마다 두 갈래로 제약). 한도 = CBS 150 노드 또는 A* 펼침 15000 번 (시계가 아니라 계산량이라 같은 입력이면 같은 결과).
  넘으면 우선순위 계획(작업 중 → 이미 엣지 위 → 실은 로봇 → 오래 기다린 로봇 순), 그래도 못 풀면 그 로봇만 예전 방식.
- **목적지에서 머무는 시간**: 로봇마다 목적지 목록(구간)을 계획한다 — 지금 목적지 + 다음 목적지(`PLAN_LEGS = 2`).
  목적지에 닿으면 거기서 할 작업 시간만큼 반드시 머문다: 정밀 주차 20 s + 적재 10 s(예상), 병실 회전 8 s, POCKET 5 s, 충전 10 s.
  그 뒤 이동이 없으면(주차 등) 계속 머묾, 내다보기 한도에서 잘린 목적지는 작업 시간만큼 머문 뒤 계획에서 빠짐(다시 출발할 때 새로 계획).
  실음/빈 상태도 구간마다(약제실에서 싣고 병실마다 내림).
  작업 중인 로봇(정밀 주차·적재·회전·POCKET·충전)도 다음 이동이 정해져 있으면 "남은 작업 시간 뒤 다음 목적지로" 계획에 넣는다(계획만).
  두 번째 목적지(예측)까지 안 풀리면 그 로봇만 예측을 줄여 다시 푼다. 누가 끝까지 서 있는 목적지는 A* 전에 거른다.
  화면 로봇 카드의 "계획: 약제실 1:58~2:02 → 4인실 오른쪽 2:25~2:33" = 목적지마다 도착~떠날 예정 시각.
- 다시 계획하는 때: 로봇이 새로 출발할 때, 실행 중 2 s 넘게 막힐 때. 움직이는 로봇 전부를 같이 푼다. 서 있는 로봇은 끝까지 그 자리에 있는 것으로 본다.
- 실행: 로봇은 계획된 출발 시각까지 기다렸다가(화면 '계획 대기') 다음 엣지로. 출발 직전 같은 충돌 함수로 "지금" 다른 로봇과
  부딪히지 않는지 본다(안전장치). 막다른 목적지 zone 미리 잡기는 그대로 — 그 안쪽에 갇힌 로봇(예: CHARGER)이 있거나 그 zone 을
  지나갈 로봇이 이미 출발했으면 먼저 보낸다.
- 고도화 여지: 실제 로봇 진행(어느 엣지 몇 %)을 받아 점유·지연 판단, 목표 뒤 머무는 시간(정밀 주차·회전), 계획 기간 제한, ECBS 등.

## 규칙 구현 요약

- **배차**: 가장 오래된 주문을 씨앗으로 노는 로봇에 묶음(가까운 병실부터, 최대 3). 배차 때 정한 목록은 바꾸지 않는다 —
  배송 중인 로봇에 끼워 넣기 없음, 여분 없음(맡은 주문 수만큼만 싣는다). 새 주문은 노는 로봇을 기다린다 (2026-10-27 사용자).
  오염도·피로도를 배차 때 미리 계산(`feasible`). 배송 묶음에는 POCKET 을 넣지 않는다: 오염도가 남은 로봇도 받지만
  100 을 넘거나 수술실이 있으면(수술실은 오염도 0 에서 맨 앞만) 그 로봇은 못 받음. 먼저 들어온 주문을 못 받으면 다음 주문부터 (10-29).
- **병실**: 도착하면 제자리 한 바퀴(`spin_s`) = 배송 완료, 그 뒤 1~5초 무작위로 쉬고(`pause_s`) 다음 일.
- **노는 로봇**: 피로도 ≤ 20 → 충전(오염돼 있으면 POCKET 먼저, 충전기 자리를 출발 때 잡음), 받을 배송이 없고 오염도 > 0 → POCKET, 그 밖엔 주차 자리.
- **예약**: 경로를 "멈춰도 되는 곳(차선 노드) 또는 목적지"까지 덩어리로 전부 잡거나 아무것도 안 잡는다.
  - 노드 1대. 14.5 cm 안의 노드, 엣지가 14.5 cm 안으로 지나가는 노드도 같이 비어야 한다
    (예: 문 앞 점 ↔ 차선 노드 9.5 cm, POCKET–CHARGER 엣지 ↔ T1_190 10 cm).
  - zone 1대(협로·계단 통로·갈림목·병실·약제실·POCKET·충전기). 차선은 엣지마다.
  - 막다른 목적지(병실·약제실·POCKET·충전기)는 출발할 때 zone 을 먼저 잡는다 → 못 잡으면 지금 자리에서 기다림
    (약제실 앞 복도에서 줄 서지 않음).
  - 실은 로봇끼리: 교행통로에서 다른 차선 x 범위가 14.5 cm 안으로 겹치면 못 들어감(차선으로 들어오는 엣지 포함).
  - 지나간 노드는 몸체가 14.5 cm 멀어질 때까지 붙잡는다.
- **교착 풀기**: 서로 기다리는 고리가 3 s 넘으면, 다른 로봇이 잡은 곳·갈 길·실은 로봇이 지날 복도 구간을 피해
  갈 수 있는 가장 가까운 차선 노드나 협로 안 경유점으로 한 대를 비킨 뒤 원래 일을 이어 간다.
- **주차 자리**: 복도 서쪽 끝 B1_20, B2_20, T1_20 + 아래 복도 동쪽 끝 B1_195. (T2_20 은 콘센트 자리라 그래프에서 뺌, 10-28) CHARGER 는 막다른 두 칸(POCKET→CHARGER)이라 뺐다.
  같은 x 의 두 차선 자리(짝)에는 약 실은 로봇을 둘 세우지 않는다 (나란히 서면 그 복도 끝을 아무도 못 지나감).
- **막다른 목적지 차례**: 같은 구역을 더 오래 기다린 로봇이 먼저. 어떤 로봇이 15 s 넘게 기다리는 구역을 새로 지나가는 이동은 보류
  (막다른 곳에 갇혀 그 구역으로만 나올 수 있는 로봇은 예외). 이게 없으면 POCKET 을 2000 s 넘게 못 받는 로봇이 생겼다.
